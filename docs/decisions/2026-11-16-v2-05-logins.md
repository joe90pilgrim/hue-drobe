# V2-05: individual logins with Identity-Aware Proxy

Date: 2026-11-16. Ticket: `docs/tickets/v2-beth-joins/V2-05-logins.md`.

## Decisions (Joe, 16 Nov 2026)

- **Sign-in: Identity-Aware Proxy (IAP) on Cloud Run** (option A). Google does the sign-in in front of the app, and only the two Google accounts in `private/users.json` are let in.
- **Joe and B cannot see each other's avatar or wardrobe, for now.** The ticket recommended read-only sharing. Each avatar pack is served only to its owner.
- **Sign in again every 30 days.** Offline use of the installed app never asks.
- **Data sync between devices: wanted, through a small Firestore database written in the background, with IAP kept for sign-in.** This is V2-06's question, and Joe answered it here. It changes two of the blueprint's settled points: "data stays on the device (IndexedDB)" and "no backend". IAP is enough for it. The Cloud Run server already knows who is signed in from IAP's signed header, so it can read and write Firestore for that person with its own service account. That means no Firebase sign-in and no keys in the app. V2-06 is updated to match. **Not built in V2-05.**

## What was built

- `deploy/server.mjs` now checks IAP's signed header (`x-goog-iap-jwt-assertion`) on every request, not the basic-auth password. It checks the ES256 signature against Google's published keys, the audience (`/projects/NUMBER/locations/REGION/services/SERVICE`), the issuer, expiry with 30 s of skew, and the token's lifetime. It also checks its own two-person allow list. It refuses to start without an audience and an allow list. Anyone else gets 403 on every path.
- Avatar packs are staged as `pack/<person>/` for every person in `private/users.json`. Someone else's pack returns 404, the same as a missing file.
- `GET /api/me` returns `{"person": "joe" | "b"}` for V2-06.
- `deploy/deploy.mjs` deploys with `--iap --no-allow-unauthenticated`, drops the basic-auth secret from the service and removes the MVP's `allUsers` invoker binding. It lets IAP's service agent call the service, gives the two emails `roles/iap.httpsResourceAccessor`, and sets IAP reauthentication to 30 days (`LOGIN`, project level, `iap_web`). The emails reach Cloud Run through an env-vars file in `deploy/out/` (git-ignored), never through the repo.
- `deploy/set-password.mjs` is removed. Basic auth is gone from the code.
- Fixed in passing: `deploy.mjs` was not shipping `tights.glb` (added in V2-04), so tights would have failed to load on the hosted app.

## Checks

- `node --test deploy/server.test.mjs`: 14 tests pass. They use a key pair made in the test in place of Google's, and synthetic emails. Covered:
  - forged, tampered, expired, future, over-long, wrong-audience, wrong-issuer and `alg`-swapped tokens
  - a stranger, a missing header and a bad header on every path, including both packs and `/api/me`
  - each person's pack hidden from the other, including `..` and encoded tricks
  - key refresh rate limits and keeping keys when a fetch fails
- The staged build (`deploy.mjs --stage-only`) was run locally as Joe (`LOCAL_PERSON`, which the server refuses on Cloud Run). The avatar loads, `/api/me` says `joe`, B's pack is 404, and the manifest and service worker load. With the server stopped, a reload still shows the app and avatar from the service worker cache.

## Deployed (16 Nov 2026)

Joe deployed to `huedrobe-joe-4821` and signed in with his Google account successfully. Two problems came up on the way, both fixed:

- **Access step failed.** `gcloud iap web add-iam-policy-binding` needs the Cloud Resource Manager API, which was off. `deploy.mjs` now turns it on with the IAP API.
- **"Empty Google Account OAuth client ID(s) secret(s)".** `--iap` turns IAP on but cannot create the OAuth client in a project without an organisation. Joe set up the branding screen (External), created a web OAuth client with IAP's redirect URI, and attached it with `gcloud iap settings set` (`--resource-type=cloud-run`). The secret was kept in git-ignored `private/`. The steps are in `deploy/README.md`.
