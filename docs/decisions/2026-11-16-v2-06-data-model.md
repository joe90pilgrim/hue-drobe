# V2-06: per-person data and the Firestore data model

Date: 2026-11-16. Ticket: `docs/tickets/v2-beth-joins/V2-06-profiles.md`.
**Status: approved by Joe, 16 Nov 2026.** All three questions at the end answered with the recommended option.

## What is stored today

One IndexedDB database, `huedrobe`, with one `kv` store and eight keys: `wardrobe`, `outfits`, `favourites`, `colourQuiz`, `outfit`, `colours`, the neckline and the sheer setting. Wardrobe items and outfits already carry an `id` and a record version `v`. The backup file (V1.1-06) is the same eight keys as one JSON object. No photos are stored yet, so all of it is a few kilobytes.

## Proposed split of the ticket

The ticket asks for a re-scope because sync is more than 1.5 hours. Proposal: two tickets, each shippable on its own.

## V2-06a: on the device

- **One IndexedDB database per person**: `huedrobe-joe` and `huedrobe-b`, same `kv` store and keys as now. The person comes from `/api/me`. Two people sharing a laptop never see each other's data, and no record needs rewriting.
- **Owner.** The owner is the database (and, in V2-06b, the Firestore path), not a field on each record. Adding an `owner` field to every record would repeat the same fact eight ways and could disagree with where the record lives. The ticket says "every stored record gains an owner"; this meets it by placement. Records keep their `v` so a field can still be added later.
- **Moving 1.1 data to Joe.** On the first start signed in as Joe, if `huedrobe` exists and `huedrobe-joe` does not, copy every key across, then mark the old database as moved (it is kept, not deleted, for one version). If B signs in first on Joe's device, she gets an empty profile and the old data waits for Joe.
- **Avatar pack**: `./pack/<person>/`, from `/api/me`.
- **Offline.** The last known person is remembered on the device, so the installed app opens offline without `/api/me`. The dev server answers `/api/me` as Joe, or as `LOCAL_PERSON` when set.
- **Backup and restore** work on the signed-in person's data only.

## V2-06b: Firestore

**Shape.** One native-mode Firestore database in the same project, region `europe-west2`.

```
people/{person}/kv/{key}
  value:      the stored value, exactly as in IndexedDB
  updatedAt:  server timestamp of the last write
```

`person` is `joe` or `b`. `key` is one of the eight keys, checked against a fixed list on the server. One document per key keeps each write small and lets settings and the wardrobe change independently.

**Who can read and write.** Only the Cloud Run server, with its own service account and the `roles/datastore.user` role. The person is always taken from IAP's signed header, never from the request, so one person cannot touch the other's path. Firestore's own security rules are set to deny everything (`allow read, write: if false`), because no browser ever talks to Firestore directly.

**Server endpoints** (behind IAP, as now):

- `GET /api/data` returns every key for the signed-in person with its `updatedAt`.
- `PUT /api/data/{key}` with `{ value, baseUpdatedAt }` writes one key. Values over 256 KB or unknown keys are refused.

**Sync in the app.**

- Every save writes IndexedDB first, as now, then adds the key to an outbox (also in IndexedDB).
- The outbox is sent in the background when online, on start, and on the browser's `online` event. A failed send stays in the outbox.
- On start, after the outbox is sent, the app fetches `/api/data` and takes any key that is newer on the server than the device's last-synced copy.

**Conflicts.** Last write to reach the server wins, per key. The one way to lose an edit: change the same key (for example, the wardrobe list) on two devices while both are offline, then bring both online. The later one wins and the earlier edit is lost. For two people, each mostly on one device at a time, this is rare. The server records when it happens (a `PUT` whose `baseUpdatedAt` is older than the stored one) so we can see whether it matters. Merging lists record by record (the `id`s allow it) is a later ticket if needed.

**No new dependency.** The server calls Firestore's REST API with a token from Cloud Run's metadata server, using Node's built-in `fetch`. This avoids `@google-cloud/firestore` (Apache-2.0, but large, with gRPC). Tests use an in-memory store behind the same interface; local trials use a JSON file in git-ignored `deploy/out/`.

**Deploy.** `deploy.mjs` turns on the Firestore API, creates the database if missing, deploys the deny-all rules and grants the role. Cost: two people are far inside Firestore's free daily quota (50,000 reads, 20,000 writes).

**Not covered.** Photos (Version 4) are too large for Firestore documents and will need Cloud Storage. That is a separate decision.

## Blueprint change

This replaces two settled points in the blueprint: "data stays on the device (IndexedDB)" becomes "IndexedDB on the device, synced to a private Firestore database through our own server", and "no backend" becomes "a small backend on Cloud Run, behind IAP". The blueprint and `CLAUDE.md` are updated once this is approved.

## Decisions (Joe, 16 Nov 2026)

1. **Split.** V2-06a Profiles (1.5 h) now; V2-06b Sync (3 h) as its own ticket, `docs/tickets/v2-beth-joins/V2-06b-sync.md`.

## Built: V2-06a (16 Nov 2026)

- `app/src/person.ts` asks `/api/me` who is signed in and remembers the answer in `localStorage`, so the installed app opens offline as the last person. With no answer and no one remembered, the app says so and loads nobody's data. Person ids are checked (`^[a-z][a-z0-9-]{0,31}$`) because they become part of a database name and a URL.
- `app/src/store.ts` opens `huedrobe-<person>`. Reading or writing before the person is known throws, so nothing is ever stored without an owner. `moveLegacyData` copies the old `huedrobe` database into Joe's on his first start, only when his is empty, then marks the old one with `__movedTo: "joe"`. It is not deleted; remove it in a later version.
- The viewer loads `./pack/<person>/`. The service worker pre-caches the signed-in person's pack and never caches `/api/`.
- The dev and preview servers answer `/api/me` as Joe, or as `LOCAL_PERSON`, and serve every pack in `private/pack/`. `.claude/launch.json` has `app-dev-b` to run as B.
- No server change was needed: V2-05 already serves `/api/me` and keeps each pack private to its owner.

### Known limits

- **Shared device, offline.** Avatar packs cached by the service worker stay on the device. On a laptop both people use, the other person's cached pack could be read from the browser's cache by someone with the device. The server still never sends one person's pack to the other. Acceptable for a family laptop; say if not.
- **Joe checked on the phone behind real IAP** (below). B's sign-in behind IAP is still unverified from V2-05.

Offline use behind IAP was also never checked in V2-05, so this may predate V2-06.
  - Ruled out: Cloud Run's log shows the phone fetched `sw.js` and every precached file and pack file at 18:51, all 200, so the offline cache did install. On the laptop behind IAP the caches are complete, with no redirects and no `Vary` headers, and both the page and its script match from the cache. The app waits at most 1.5 s for `/api/me` before starting as the remembered person, and reloads if the server later names someone else.
